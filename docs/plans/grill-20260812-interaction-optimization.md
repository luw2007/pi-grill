## ① 背景与问题

现有 `/grill` Pi extension 交互围绕 `grill_ask` 单/多题 TUI 面板：单题用上下键选选项、Enter 确认；多题用 Tab/方向键切题，每题选完仍需切到「提交」tab 才能一次性提交。每次选完选项后额外弹出一次自由文本「理由」输入（可空但仍需按键确认或输入），随后若选到"其他"还要再弹一次输入框。收敛确认依赖对用户所选选项 label/value 文本做正则关键词匹配（`confirm|converge|yes|确认|生成`），不够显式。

用户确认的具体摩擦点：A 每题强制理由输入、C 单题视图信息密度低看不到整体进度、D "其他"选项二次弹窗、E 收敛确认依赖关键词匹配；另指出「传统 tab 无法动态增减」——当前 `askQuestions` 的 tab 面板由传入的固定 `questions` 数组渲染，运行期无法响应后台 subagent 对问题清单的增删。用户明确排除多题 Tab 切换路径本身不是问题。

## ② 目标与非目标

### 目标

- 把「理由输入」与「其他选项输入」都合并进同一个选项面板内联完成，取消额外弹窗。
- 单题、多题模式统一常驻进度条 + 题目列表侧栏，随时可见整体进度和已答内容。
- 保留收敛确认的关键词匹配机制，关键词列表迁移到独立 JSON 配置文件，运行时读取。
- 面板支持热更新：后台 subagent 写回 JSON 后，当前打开的 tab 面板能同步反映 pending/current 的增减；新 current 出现时仅在 tab 栏做视觉提醒，不打断用户当前操作、不强制跳转。

### 非目标

- 不放弃现有 TUI 交互形式，不引入浏览器桥接或 literal HTML 渲染（沿用既定架构决策）。
- 不把收敛确认改造成结构化独立选项集——用户明确选择保留关键词匹配路线。
- 不追求多题 Tab 切换路径本身的改动——用户确认现有 Tab/方向键切题路径不是问题。
- 不做热更新后的自动焦点跳转——用户明确选择"仅提醒，不打断"。

## ③ 现状调研结论

已核查：`/Users/luwei.will/ai/grill` 工作目录为空且不是 Git 仓库；现有 Pi extension 位于 `~/.pi/agent/extensions/grill.ts`，原 Claude command 位于 `~/.claude/commands/grill.md`。

`grill_ask` 当前流程：`addQuestions` → `askQuestions`（自定义 TUI 组件，Tab 切题/↑↓选选项/Enter 确认，多题额外有"提交"tab）→ 逐题弹出理由 `context.ui.input` → 若选"其他"再弹一次输入框 → `applyAnswers` 按 `batchIds` 顺序写回状态 → 若 `converge` 且十个 section 齐且用户选项文本含"确认/收敛"等关键词，弹 `context.ui.confirm` 最终确认。

`askQuestions` 内部 `questions` 参数在整个自定义面板生命周期内固定，没有响应外部状态变化的机制；`Runtime` 已持有 `fs.watch` 监听 JSON 文件变化（用于 `syncFromDisk`），可作为热更新的触发源。

## ④ 方案设计

- **理由输入**：不再是每题必经的独立弹窗。选完选项后同一面板内联出现可选文本框，Enter 直接跳过，输入文本后 Enter 才携带理由提交。
- **"其他"选项**：选中"其他"后不再弹二次输入框，在同一面板内联出现自定义文本框，与理由输入统一为一屏内完成。
- **进度展示**：单题模式与多题模式统一常驻一行进度条（如"第 2/5 题 · 已答 1"），同时始终展示简要题目列表侧栏（题号+状态图标），两者都要，不因单/多题模式区分。
- **收敛确认**：保留现有关键词正则匹配机制，但把关键词列表改为可配置项（而非硬编码 `confirm|converge|yes|确认|生成`），不改为结构化独立选项集，也不去掉二次 `ctx.ui.confirm`。
- **面板热更新**：`askQuestions` 面板复用现有 `Runtime.watcher`（`fs.watch` 监听 JSON）作为触发源；JSON 合法变化时，若面板仍处于打开状态，重新读取 pending/current 题目集合并同步更新 tab 栏（新增题追加为新 tab，被移除的题按 race rule 处理——若用户正在该 tab 上 composing 尚未提交的答案，允许其提交后走 race rule 转 `deprecated`）。
- **关键词配置来源**：独立 JSON 配置文件 `~/.pi/agent/grill.config.json`，运行时读取；未提供或格式非法时按现有"拒绝并保留上一份有效展示"原则处理，回退到内置默认关键词列表并提示，而非静默使用非法配置。
- **热更新焦点行为**：新题被提升为 `current` 时，不自动切换用户当前所在 tab；仅在 tab 栏对该 tab 做视觉提醒（如高亮/角标），由用户手动切换查看。

## ⑤ 备选方案与权衡

- **理由输入**：曾考虑"默认跳过、按需追加"、"完全去掉理由"、"预填推荐理由"；均被否决——前两者仍保留独立交互步骤或丢失可审计信息，均不如"同屏合并、可选跳过"直接。
- **"其他"选项**：曾考虑"保留独立弹窗但省略理由"；否决，因为仍多一次上下文切换，不如与理由输入统一为同屏输入。
- **进度展示**：单独进度条成本最低但信息量有限；用户选择进度条+侧栏都要，接受侧栏对窄终端宽度的额外渲染成本，换取更高的信息密度。
- **收敛确认**：结构化独立选项集能从根本上消除误判，但需要改变 `grill_ask` 的调用约定（新增专门的"收敛问题"类型）；用户选择保留关键词匹配+可配置，以较小改动换取兼容现有调用方式，代价是仍存在文本匹配的理论误判风险（已用可配置缓解，非结构化根治）。
- **面板热更新**：不追求面板内热更新实现成本最低、状态同步风险最小；用户选择支持热更新，接受更高的实现与测试复杂度（面板生命周期内响应外部 JSON 变化、tab 集合运行期增减、race rule 与面板同步的交互），换取与 subagent 后台更新的真正实时一致性。
- **关键词配置位置**：源码顶部常量最简单但需改源码；每次调用传参灵活但重复繁琐；独立 JSON 配置文件在"无需改源码"与"无需每次重复传参"之间取得平衡，被采纳。
- **热更新焦点行为**：自动跳转保证第一时间可见但打断当前操作；仅在提交汇总页跳转是折中但状态条件复杂、边界模糊；仅视觉提醒不跳转最不打断用户，被采纳。

## ⑥ 接口/数据结构变更

- `askQuestions(context, questions)` 签名需扩展：新增可选的热更新数据源（如 `watchState: () => GrillQuestion[]` 或直接传入 `Runtime`），使组件能在渲染前重新拉取 pending/current 集合；tab 提醒态需要一个轻量标记（如 `hasUpdate: boolean`）区分"新增未读"与已浏览过的 tab。
- `AskAnswer` 需要在原字段基础上于同一组件内捕获 `reason`（理由）与 `otherLabel`（其他选项自定义文本），不再依赖调用方在 `grill_ask` 执行体里二次调用 `context.ui.input`。
- 新增收敛关键词配置读取：`~/.pi/agent/grill.config.json`（形如 `{ "convergeKeywords": ["confirm", "converge", "yes", "确认", "生成"] }`），启动/收敛检查时读取并校验为非空字符串数组；非法时回退默认值并 `notify` 提示。

## ⑦ 风险与影响面

- 面板热更新引入运行期状态同步复杂度：需要处理"用户正在编辑的 tab 被后台移除"（race rule 已覆盖）、"渲染节流"（频繁 JSON 写入可能导致面板抖动）等边界，需在实现阶段加防抖。
- 关键词可配置化如果配置来源缺失或格式错误，需按现有"非法变更需拒绝并保留上一份有效展示"的原则处理，不能静默回退成硬编码默认值而不提示。
- 侧栏常驻会压缩窄终端下的可用渲染宽度，需要在窄宽度下做降级（如自动隐藏侧栏，仅保留进度条）。

## ⑧ 测试计划/验证方式

- 手动 TUI 回归：单题/多题模式下验证理由与"其他"输入合并到同一面板、Enter 跳过路径、进度条与侧栏常驻展示。
- 热更新回归：在面板打开期间，通过外部脚本修改 JSON 增删 pending 题，验证 tab 栏同步更新且不丢失用户已选但未提交的答案；验证新 current 只提醒不自动跳转。
- 收敛关键词可配置回归：修改 `grill.config.json` 后验证新增/移除关键词按预期生效；文件缺失或格式非法时验证回退默认值并有提示，而非静默失败。

## ⑨ 回滚/清理方案

本轮为交互层重构，不涉及外部状态 JSON schema 变更；如需回滚，直接回退 `grill.ts` 对应函数（`askQuestions`、`applyAnswers`、收敛确认逻辑、配置读取）到修改前版本即可，无需数据迁移或清理 `/tmp/grill` 下已有状态文件。新增的 `grill.config.json` 若不存在则自动回退默认关键词，删除该文件不影响现有功能。

## ⑩ 开放问题/待跟进事项

- 面板热更新的节流/防抖策略、渲染性能边界，留待实现阶段结合真实 subagent 写入频率验证。
- 若后续需要支持多个 Pi 会话/多个 subagent 并发写入同一 JSON，面板热更新与 race rule 的交互需要更细致的并发测试，本轮访谈未覆盖。
